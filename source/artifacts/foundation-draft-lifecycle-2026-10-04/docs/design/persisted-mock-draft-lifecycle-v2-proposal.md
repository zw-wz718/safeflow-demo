## 1. 结论与范围

现有机制不能在保持合同10的同用户、同任务要求下直接接上持久修改/取消：合同24将创建任务置为 COMPLETED，合同08不允许终态复活，`replace_plan`拒绝已有操作，新操作和计划更新又被永久的每任务一次领取阻止。改名字、另建任务接管旧草案、删除领取或重写旧终态都不是解决方案。

建议新增独立的 `MOCK_DRAFT_LIFECYCLE_V2` 生命周期标记及公共 HTTP scope `MOCK_DRAFT_LIFECYCLE_ONLY`，仅供通过新入口创建的新任务使用。创建成功后完成的是创建操作，任务进入真实持久的 WAITING_USER；此后在同一 task_id 下增加经检查的动作、计划版本、公共 operation_id 和明确确认。每个动作永久领取一次，整个任务始终最多有一个未结算领取。取消业务草案成功才将任务终结为 CANCELLED。

这是公共任务机制的版本演进，不修改逐风现有业务。业务仍采用合同10已经交付的 Tool/Policy/Store：创建业务版本1、修改+1、取消不增、原草案及业务操作ID不变、同用户同任务、到期不可修改/取消。业务内存不因公共状态持久化而成为可恢复的业务数据库。

合同24/25的原路由、scope、版本1响应、旧领取表和旧任务均保持原义。包括尚未执行的旧创建任务，也不转换为新生命周期；Completed/Failed/Cancelled 永不恢复。新入口明确选择新语义，而非用请求参数给旧任务改模式。正式资金、PRE_COMMIT、生产Permit、正式认证、Outbox及多实例业务恢复不属于此提案。

## 3. 新创建阶段与计划结构

生命周期版本与 Tool 授权版本、Schema版本、业务版本是不同概念。新创建使用已有Create授权v1，修改/取消使用已有授权v2；Tool Schema仍使用各实际注册值。不能把公共生命周期v2填入这些既有版本字段。

服务端经过现有计划检查后一次保存：原task_id/owner、新生命周期标记、初始计划P1、不可变检查来源、预留公共操作O1及准备日志。身份来自版本化SessionResolver。客户端不能提交owner、初始状态、模式切换、可信来源或任意操作号来接管任务。创建请求必须有新scope/版本的显式选择；未知/未配置模式拒绝，不降级执行合同24。

逻辑节点示例（C/M/X是Tool，D是UserDecision；名字仅用于说明，实际服务端分配唯一NodeId）：

```text
P1: C1(Create) -> D1(等待用户选择下一动作)
P2: C1 -> D1 -> M2(Modify) -> D2(等待用户选择下一动作)
P3: C1 -> D1 -> M2 -> D2 -> X3(Cancel)
```

P2/P3保留已完成节点的ID、工具、完整参数和依赖，不能改写C1/M2来伪装历史。等待节点完成表示服务端接收了用户选择并保存新计划，不表示用户已确认写操作。只有当前动作节点对应的一个公共操作可以准备、确认和领取；历史操作不能重新进入安全门禁。

每次选择在task-first事务里比较原task revision与当前等待节点，保存检查通过的新计划、计划历史、动作关联及新DRAFT操作，再由 `UserResponded` 转回RUNNING并移动到新Tool。恢复该选择按原动作准备号查询，不重新分配operation_id。计划检查失败不保存未核验计划。

旧 `replace_plan/create_operation/checkpoint/只读续跑/合同22和24执行` 方法不能操作新模式任务；增加显式模式拒绝，不放松这些方法原有检查。新生命周期由专用可信后端服务处理。读取可共享基础数据，但新模式必须走其验证和恢复分支；不能直接把普通 `ReviewNode` 当作重新执行未知写的指令。

## 4. 状态、版本与确认的逐步例子

以下均属同一用户U、任务T。B表示业务草案版本，P表示Runtime计划版本，F表示可信事实版本，R表示数据库revision；B/P/F/R互不替代。

| 步骤 | 当前计划/操作 | 公共任务与检查点 | 公共操作状态 | 业务状态/版本 | 绑定与允许下一步 |
|---|---|---|---|---|---|
| 检查新创建并保存 | P1/O1，C1->D1 | RUNNING，AtNode(C1) | DRAFT | 草案未创建 | 保存初始检查来源；准备两阶段真实预检和展示 |
| 展示、明确确认创建 | P1/O1 | RUNNING，AtNode(C1) | DRAFT | 草案未创建 | 新确认绑定U/T/O1/C1/P1/F/R/参数/会话；CONFIRMED不自动执行 |
| 领取创建 | P1/O1领取提交 | RUNNING，AtNode(C1) | DRAFT | 未知；可能已经保存 | 任务屏障生效；并发只查O1，不能执行第二次 |
| 创建已核验且结算 | P1/O1 | AwaitUser -> WAITING_USER，AtNode(D1)；C1完成 | SUCCEEDED | READY_TO_CONFIRM，B1 | O1历史永久保留；旧确认因状态/revision变化不可执行 |
| 用户选择修改 | P2/O2，追加M2->D2 | D1完成；UserResponded -> RUNNING，AtNode(M2) | O1保留SUCCEEDED；O2 DRAFT | 仍B1 | 实际Store身份/版本核对；参数严格为draft_id/expected_version=1/changes；新裁决/展示/确认 |
| 明确确认并领取修改 | P2/O2 | RUNNING，AtNode(M2) | O2 DRAFT，永久领取 | 未知，可能B1或B2 | 新确认不借用创建确认；只准原O2完成核验/结算 |
| 修改已核验且结算 | P2/O2 | AwaitUser -> WAITING_USER，AtNode(D2)；M2完成 | O2 SUCCEEDED | READY_TO_CONFIRM，B2 | 期限、草案ID及业务操作ID保留；旧历史不更新为B2 |
| 选择取消、展示并再次确认 | P3/O3，追加X3 | D2完成；UserResponded -> RUNNING，AtNode(X3) | O3 DRAFT | 仍B2 | 严格输入draft_id/expected_version=2；独立新裁决/确认，不复用修改确认 |
| 取消领取及成功结算 | P3/O3 | 核验后Cancel -> CANCELLED，Finished | O3 SUCCEEDED | CANCELLED，仍B2 | 是取消工具成功，不是把O3记成Operation CANCELLED；任务不可再修改/续跑 |

R在数据库实际改变时递增，不能写死具体revision；准备/确认本身沿用不更改任务和操作revision的规则，避免展示后暗改绑定。新动作正常取P+1；失败已提交的计划也占用该版本，后续新请求必须更高；溢出拒绝。未提交的拒绝事务不消耗计划版本。F由已有可信事实维护，不用B或P替代，不能自行刷新F掩盖事实缺失。

### 再改口与拒绝确认

同一动作尚未领取时，用户改变参数、改选动作，或旧来源已过期需要重新展示：显式建立更高P的新动作和新operation_id。锁内确认旧动作**没有领取**，将旧DRAFT/READY操作按现有Cancel事件终结并归档，失效旧展示；新参数重新检查、预检、展示、确认。它不是执行重试，旧动作从未获领取。

历史计划保存完整旧节点。当前计划保留完成的前缀，移除已经归档的未执行尾部并换成新Tool/等待尾部；旧取消操作仍在操作历史中。新检查点验证必须明确区分归档尾部和当前节点，不能让旧失败/取消节点被当作已成功完成。已领取动作不允许这个路径，无论换动作还是换P都拒绝。

第一次Create尚未领取、确认已过期或被拒绝时，允许用户在同一T明确选择重新准备：检查没有任何Create领取和已结算草案，归档旧未执行C/D，保存更高P的重新检查的C/D及新O，创建业务仍只会产生B1。首版沿用固定创建参数，不开放任意参数编辑；它是创建阶段的新确认，不是刷新旧快照期限。第一次Create一旦领取，不论成功还是未知，这条路径永久关闭。后续动作入口只接受Modify/Cancel，不能再创建第二个草案。

REJECT沿用只撤销尚未确认记录的语义，不取消业务草案、不宣称写失败。需要重新准备时走上述显式改版，不为同快照自动续期。CONFIRMED后的普通REJECT冲突；用户仍可在无领取时通过明确的新计划替换意图。旧票据/确认从此无效。

为控制最小范围，本版本不提供“结束但保留可继续草案”的业务完成动作；关闭页面、退出登录、不再回复、业务到期都不自动把任务置为COMPLETED或成功取消。缺失/过期时拒绝新写、撤去当前执行动作，只允许观察/历史核对。后续任务清理/保留期限另作公共产品决策，不能清除永久领取。

## 5. 持久模型与唯一性提案

下列是待评审的底座内部表/约束设计，不是已存在的迁移或业务接口。共用原 `tasks/operations/audit_events`；所有新表外键保留真实公共身份。SQL真源仍只在storage。

| 建议新增表 | 关键内容和约束 |
|---|---|
| `mock_draft_lifecycle_tasks` | task_id主键且外键；不可变lifecycle_version/scope、初始checked来源；当前动作引用、最近已结算动作引用、实际创建回执的草案/业务ID关联。标记只能随新创建原子插入，不能事后给旧task补标记 |
| `mock_draft_lifecycle_plans` | `(task_id, plan_version)`主键；不可变完整AgentPlan及摘要、真实检查来源/装配版本、前一版本、已完成前缀与尾部归档关系。不得覆盖旧版本；当前任务指向最高已提交版本 |
| `mock_draft_lifecycle_actions` | operation_id主键且关联原operations；task/node/plan/action/完整来源绑定与摘要、原动作准备号、实际Store观察摘要、当前或归档身份；`UNIQUE(task_id,node_id)`和`UNIQUE(task_id,plan_version)`。一个版本至多一个新的写动作；Create仅限尚无Create领取/业务草案的创建阶段 |
| `mock_draft_lifecycle_displays` | 动作/原会话摘要及binding_version的准备journal；原两阶段请求ID、裁决引用、确认引用、随机票据、冻结展示摘要和截止；沿用合同22的真实来源流程，但新版本域分隔，不能跨scope串用 |
| `mock_draft_lifecycle_claims` | operation_id主键；claim_id全局唯一；`UNIQUE(task_id,node_id)`、`UNIQUE(task_id,plan_version)`；不可变动作、领取源快照/摘要、来源引用、领取时间；状态仅CLAIMED或SUCCEEDED，后者须有核验后历史回执与结算审计。永久保留，不由TTL删除或重置 |

未结算屏障使用 `UNIQUE(task_id) WHERE status='CLAIMED'`，并在所有新模式变更事务先锁任务、再检查任意CLAIMED领取。动作名不能成为避开唯一性的键；同O换action/参数/确认/计划/会话不能另领，新的O/P也不能越过屏障。全局原operations主键防公共操作跨任务复用；同任务同节点仍只有原操作。

另外在领取表设置 `UNIQUE(task_id) WHERE action='CREATE_MOCK_DRAFT'`，包括已经SUCCEEDED的Create领取，保证每个新模式任务最多一次实际创建。仅有未领取且已归档的初次准备记录才可按上节改版；领取永久占用，不能靠已结算、换P/O或再次确认创建来规避。

task行锁保证原子选择“旧动作被替换”或“旧动作已获领取”，不能两者成功。并发两个新动作根据revision只有一个胜出；读回同一动作准备号且内容一致返回原记录，参数/工具/动作或来源不一致返回冲突。重复执行检查原领取优先于新的确认到期检查，只从当前有效会话/本人任务读历史，不重发许可；历史读取不要求重新批准旧确认。

计划/检查点/确认/裁决的新模式校验至少验证：

- 当前任务模式、初始checked来源及完整版本链；当前Tool对应唯一活动动作/O，其P/F/参数摘要匹配当前计划，未提交、无未结算领取。
- 所有成功历史操作匹配其领取时的不可变计划、真实回执及审计，不把历史operation.plan_version改成当前P；已完成节点在新计划中的定义不变。
- 被替换的旧DRAFT/READY操作只在无领取且已明确归档为CANCELLED时可离开当前计划。未知领取节点不得归档/删除。
- 确认仍精确绑定合同11全部字段及原会话；生命周期模式/动作/计划历史锚点另由封闭服务端来源核对，不能通过客户端布尔值补证。
- 裁决仍绑定完整当前任务与**全部**操作快照，并增加生命周期/计划历史/活动动作来源摘要；历史操作保留在摘要中，不能只取一个活动操作使历史篡改隐身。

复用原确认字段不是静默扩大合同11/14/18的含义。必须形成新模式可用的来源与快照验证版本；旧模式保持原算法和摘要。新来源配置/代码哈希、输入声明版本、scope/domain separator及部署版本都纳入装配核验。对未知新版本拒绝，不把v1来源当v2来源。

具体建议复用原确认/裁决表，并追加可空的生命周期锚点摘要列：旧行保持NULL，旧服务只接受原模式且锚点为空；新可信生命周期准备方法写入非空锚点，裁决使用独立 `TRUSTED_RUNTIME_LIFECYCLE_V2` source_mode，确认binding摘要使用v2域分隔。锚点覆盖模式、活动动作、原O/P、当前计划历史摘要及装配版本，展示日志保存实际引用和冻结锚点。新核验须同时检查原全部绑定字段和这个锚点；旧通用确认/裁决/组合方法拒绝新模式，不能接受仅字段相似的v1记录。现有表的来源/摘要约束只通过新迁移追加扩展；不回填旧行、不改变旧自然唯一键，也不从客户端收取锚点或source_mode。公共方法采用专用可信生命周期分支，内部共享锁、时间和真实评估实现，不另造成功提供器。

当前确认/预检快照不包含领取状态及其审计尾部；CLAIMED插入不更改task/operation revision或活动动作定义，避免领取使自身来源失效。领取时冻结原TaskRecord/全部OperationRecord/锚点/来源摘要，之后原持有者逐项复核这些来源并单独检查“仅自己的原领取未结算”。结算成功改变状态/revision，使该快照失效。历史读取按领取时的完整快照、计划历史和对应审计验证，不把后续合法计划或审计事件误报为旧回执损坏。

## 6. 写入顺序、Runtime与失效

1. 准备新动作前实际读Store并核对同U/T、原草案/业务ID、状态、期限与B，使用已有Policy/可信查询验证所需资源。此观察只作准备来源，不能替代保存前核验；非预期业务版本/缺失直接拒绝。
2. 用户只确认冻结展示的具体动作和参数。展示修改时包括原值、changes及由真实草案计算的目标值；取消时包括原草案状态、B与保留的期限。确认不自动写；客户端比较字段不是可信材料。
3. 明确execute在task-first事务锁实际当前任务/活动操作/展示/两份裁决/确认，核对全部来源、装配、会话及最早截止。保存永久CLAIMED及其审计并提交。只有首次插入且COMMIT已明确成功的原调用可以继续；重复命令只查询原领取。
4. 原调用重新锁住任务与实际来源，检查原领取身份和屏障；用原claim_id作为服务器请求幂等标识，构造绑定**原公共operation_id、原完整上下文**的私有Runtime请求。接入真实已有三个Tool/Policy，禁止普通Runtime写入口和生产Permit替代。独立时间围栏沿用合同18的微秒不倒退规则；有效期取确认/裁决/业务期限中实际约束的最早者，不另发新TTL。
5. 最后异步查询后、同步保存前，复用合同10的版本化会话与授权锁/Store锁，检查当前action/P、许可、实际B及期限。数据库锁与会话真源/Store不是跨系统原子事务；保留现有外部撤销边界，不声称生产级原子认证。
6. Tool实际保存，登记真实回执；Runtime核验ToolResult身份/正文、POST_EXECUTE真实Policy回查、当前会话及底座审计成功，生成字段私有的 `VerifiedMockDraftActionOutcome`（名称为提案）。该对象不能由JSON、模型或客户端构造，也不能代表整项任务已完成。
7. 同一PostgreSQL结算事务核对原领取与所有原来源，用实际业务ID和回执依次记录 GatesSatisfied / SubmissionRecorded / ExecutionSucceeded，最终操作为SUCCEEDED；这是已有合同24用法的历史事实记录，未验证前不能编造业务引用或提前进入SUBMITTED。随后完成本动作节点、保存历史回执、更新任务至下一D等待或取消终态、记录审计并将领取置SUCCEEDED，一起提交。

新增Runtime动作执行入口只执行被绑定的一个Tool，不回放已完成前缀、不自动跨越UserDecision、不构造虚假“整个任务已完成”。它保留现有ToolStarted/ToolCompleted/安全检查；新模式增加明确的动作核验事件，Create/Modify之后不发TaskCompleted。旧单节点入口及旧TaskCompleted历史原义保持。必须审查Runtime/存储的这条完整链路，不能仅换返回标签。

下一计划保存使旧确认、裁决、展示票据因P/R/动作/O/快照变化失效；该事务同时归档旧展示。历史行和confirmed_at/expires_at保留，不伪改历史为从未确认。旧数据库来源的动态拒绝足以阻止旧execute，内存authority的旧资格同时撤销；即使撤销步骤失败，持久模式锁内的原来源检查也必须拒绝旧写，不依赖内存撤销成功。新确认继续遵守 `(user,task)` 跨动作/节点的唯一当前版本。

创建/修改成功结算改变R及operation状态，旧当前裁决/确认立即不能再获执行；新动作必须重新评估与展示。装配、事实、会话版本、期限变化同样拒绝旧来源，不自动重评、续期或放行。历史读取验证领取时锚点/实际结算记录与当前归属，不能要求历史P等于最新P，也不能伪称历史回执是当前可执行草案。

## 7. 中断、未知结果与重启

此方案选择永久“至多执行一次”，不承诺跨PostgreSQL与内存的原子成功或中断后必能继续。

| 发生点 | 持久事实与处理 |
|---|---|
| 领取前校验失败/事务确定回滚 | 没有领取，也没有Tool写；保持已有计划/操作。用户修正意图只能经明确新计划重新检查；不自动execute |
| 领取COMMIT响应丢失 | 可能已经有CLAIMED；停止Tool调用，按原T/O查询。不能根据未收到响应重领或换号 |
| CLAIMED已提交但尚未调用Tool就中断 | 仍保留CLAIMED；不能据进程日志或“看起来没调用”解除屏障，任务只查原O |
| Tool等待/失败/超时/会话撤销 | 领取后无法得到完整核验结果即未知；不把Runtime error等同无业务变化。未保存也可能被保守阻塞 |
| 内存已保存，但回执/POST_EXECUTE/审计/结算失败 | 业务可能已改变；CLAIMED保持，原操作查询；不重做，不把历史或Store观察升级为结算依据 |
| 结算COMMIT成功、响应丢失 | 原查询可读SUCCEEDED回执及任务真实等待/取消状态；不执行Tool、追加新领取或重落结算审计 |
| 原调用仍在执行且完整结果返回 | 只能原领取持有者按原源结算；并发查询无权代结算。只有结算确定成功才允许下一动作 |
| 重启且原领取未结算 | 无论Store存在与否，只查询原O；没有业务原号查单适配，首版不提供解除未知屏障的接口或自动后台重试 |
| 重启丢失Store但领取已成功结算 | 原历史照常可读，实际观察返回DEPENDENCY_UNAVAILABLE；不从回执重建草案，不重跑Create，不改owner/task，不启用后续修改/取消 |
| Store实际B高于最近已结算B、ID/状态不匹配 | 不猜是哪个未登记动作；停止准备/执行，核对原历史，不能采用新B自动继续 |

公共状态在领取未结算时可能仍为RUNNING/DRAFT（延续合同24的诚实表示），新模式恢复结果必须把CLAIMED屏障优先于Task/Operation状态，明确仅 `QUERY_ORIGINAL_OPERATION`。不造业务号强行进入Processing，也不把它按普通DRAFT续跑。服务重建、换session、改action、升P、另分O、取消、管理清理或TTL过期都不能清除该屏障。

首版领取后只有完整可信成功可以结算。确定“无写”的失败解封机制需另有封闭来源合同与证明，本文不假设现有Tool错误已经提供此证明。没有可信结果时宁可保持未结算；不能把FAIL或CANCEL当作清理未知领取的后门。

历史回执应保留action、原公共O、原业务ID、动作P、输入expected_version（Create无此输入）、实际输出B、tool_result_ref和执行时间，以及既有已核验正文/摘要，字段采用现有ToolResult真实输出。新scope的历史状态表达动作成功与任务当前状态分离；`receipt_scope=HISTORICAL_EXECUTION_RECEIPT`、`current_draft_verified=false`仍成立。实际Store观察仍是独立只读结果，不是历史查询的回退数据。

## 8. HTTP隔离与最小公共入口提案

建议使用独立 `/api/sim/draft-lifecycles` 路由族，mode仍是PROJECT_SIMULATION，响应 `contract_version=2`、scope为MOCK_DRAFT_LIFECYCLE_ONLY。以下只是公共底座接口候选，均待合同评审；本轮不挂路由。

| 候选入口 | 意图与硬边界 |
|---|---|
| POST `/api/sim/draft-lifecycles` | 明确新版本创建；只保存checked新任务、C1/D1及预留O1，不自动写业务。首版创建沿用合同22固定已核对样例，不扩展任意创建参数 |
| GET `/api/sim/draft-lifecycles/:task_id` | 当前任务、活动动作/等待点与历史原号的安全投影；GET不准备/刷新/执行 |
| POST `.../:task_id/actions` | 当前等待节点选择Modify/Cancel，或显式替换未领取尾部；创建阶段只允许上述未领取的固定Create重准备，已有Create领取即拒绝。比较原revision/P及服务端保留的准备号；业务payload仅已确认输入，不接受owner/业务状态/许可/可信结果 |
| POST `.../:task_id/operations/:operation_id/prepare` | 原动作journal恢复真实预检/展示；同快照/原会话不续期。缺源明确拒绝 |
| POST `.../:task_id/operations/:operation_id/confirm` | 原scope/O/confirmation_ref/display_ticket的CONFIRM或REJECT；采集明确动作，不执行 |
| POST `.../:task_id/operations/:operation_id/execute` | 原确认及公共revision/P/F比较，服务器重读真实源；一次领取后仅查询，不允许客户端params/action/业务ID覆盖当前动作 |
| GET `.../:task_id/operations/:operation_id` 及其 `/current-draft` | 原动作历史和独立实际Store观察；不能在新scope中借旧24查询的“当前任务仍等于初始来源”假设 |

创建/选择首响应丢失且客户端未获服务端原号时停止新增，人工核对；如需解决这一可用性缺口，必须先审查明确的创建请求幂等合同，不能自动再造任务。本版本不引入推测的业务request字段。所有HTTP外围继续复用当前Host/Origin、版本化Cookie、CSRF、严格重复/未知字段拒绝、正文/数字上限、no-store与错误脱敏。最终DTO字段/原因沿用现有公共原因后专门冻结，不猜业务新错误码。

## 9. 必要的公共兼容扩展与外部问题

### 公共输入验证

合同14的平面Schema不能验证现有Modify的嵌套 `changes`；现实现会拒绝，不能删除该字段、展开参数绕过真实Tool，或关闭未知关键词校验。

建议新增显式v2直接输入验证器：根规则保持；只增加一层封闭object属性及 `minProperties`，其叶子仍为已支持的标量类型/约束。嵌套object的 `required` 缺省等价空数组（实际changes Schema未声明required），有则校验重复、未知键及必填；不改写实际Schema再计算摘要。所有可选属性的Schema仍预先检查，`additionalProperties=false`强制，空changes、null、嵌套未知字段/关键词、第二层object、array/ref/组合/浮点继续拒绝。保持4KiB输入、16KiB Schema及64字段的全树累计上限，已有字符串/整数/正则口径不放宽。业务Policy仍核验精确金额、归属、期限和状态。旧v1验证与来源哈希保持；新部署显式选v2并增加对应输入声明/代码哈希。

### 业务问题的最小集合

本方案不改变合同10已确认语义，因此**当前范围没有阻塞设计的新增业务问题**，不需要要求逐风重新批准已交付字段/状态/Tool。跨任务转移、旧终态复活、重新生成草案、自动延长TTL、业务数据库化、资金取消、缺失内存重建都明确排除。

以下仅在未来要扩大相应能力时才向对应负责人确认，不阻止本公共方案审查：

| 扩展条件 | 需实际材料 | 负责人 / 受影响范围 / 恢复条件 |
|---|---|---|
| 要跨重启继续修改/取消业务草案 | 真实业务存储、事务及恢复/回执来源合同和代码，原U/T/ID/B/期限保持规则 | 逐风提供业务材料、底座接入；只阻塞业务持久恢复；材料核对并共同确认后恢复 |
| 要解除未知领取 | 按原公共O映射原业务ID的可信结果查询及“未写/已写”证明，含无ID时语义 | 业务部分逐风，公共结算底座；只阻塞未知解封；来源可核验后再设计，不从Store观察推断 |
| 要正式资金提交/撤销 | 正式幂等/账务/查单、认证、完整指纹、PRE_COMMIT/Permit、Outbox合同 | 现有对应负责人；不属于模拟草案生命周期，不影响本方案的公共准备工作 |

当前真正待决的是底座合同评审：新模式及路由版本、动作与任务完成分离、多版本历史验证、CLAIMED永久屏障、输入v2、迁移/部署规则。由底座提出，检查侧独立评审后下发实施范围；正式合同批准人员尚待确认。没有把这些问题分配给业务负责人。

## 10. 最小实施包与迁移兼容

应作为一个可交接的完整生命周期实施包：新创建 -> 创建确认/执行 -> 持久等待 -> 修改重新确认/执行 -> 持久等待 -> 取消重新确认/执行 -> 终结，加上所有失败屏障；不能只开放新Create留下一条未经验证的后续写路径。

| 实施项 | 归属/已有依据 | 开工条件 |
|---|---|---|
| 新模式公共类型、版本/scope及封闭动作结果 | 底座；现有状态枚举、合同10三动作及原PRD | 先评审新语义；不增加业务枚举或修改旧终态转换 |
| 专用计划/动作/历史/展示/领取服务及唯一性、检查点验证 | 底座storage；复用已有task-first/会话/时间围栏/审计 | 先冻结新来源与迁移约束；不解除通用旧方法限制 |
| bounded嵌套输入验证v2及新装配来源 | 底座runtime；直接采用现有Modify Schema | 先评审合同14兼容扩展；必须先于Modify预检接入 |
| 真实三Tool/Policy接入、当前Store回读与目标展示 | 既有业务代码，底座只做装配 | 业务参数/状态/版本可直接依据合同10；持久调度须等本新合同评审，不代写业务服务 |
| 动作Runtime封闭核验、领取后执行及原回执结算 | 底座runtime/storage；复用已有真实保存/回执/POST_EXECUTE | 先审查整个动作与任务分离；不能继续使用会发TaskCompleted的旧单节点结果冒充完整新计划执行 |
| 独立HTTP与普通任务查询安全投影 | 底座api；外围可直接复用现有HTTP规则 | 新DTO/路由/恢复投影评审后挂载；缺配置/旧模式/未知领取必须拒绝 |
| 永久测试、迁移兼容和完整交接 | 底座；已有实际业务工具作为集成依赖 | 上述范围同时完成并验证后整体交付；生成自测与检查验收分别登记 |

只依据旧合同可复用的是现有业务输入/结果/Tool/Policy、会话外围、锁序及拒绝原则；“可复用”不构成本轮实施授权。本轮仅设计与台账登记。新持久动作、模式选择、结构化等待/改版、领取、来源验证及HTTP行为均必须先完成合同评审。后续改动限定公共模块及新增迁移，不修改成员业务代码。

迁移仅追加当前最后迁移之后的新文件，不改旧SQL及校验和，不改Cargo锁。新表初始化为空；不回填旧任务模式、不删除/搬移旧领取、不转换既有Completed任务。重复迁移无副作用，非法旧数据/新来源关联拒绝且回滚，不修复为伪成功。新表状态/版本/身份/外键/源摘要/回执组合约束防止SQL NULL放行；具体DDL在评审后确定。

保持旧来源的验证算法并不表示无视真实装配变更。若升级确实改变旧模式受绑定的代码/配置摘要，仍按合同14的ASSEMBLY_CHANGED使旧当前来源失效，要求明确重新准备；不能伪报旧代码哈希。既有历史按当时来源保存与核对，不因新装配重写或丢弃。优先将v2验证及执行分支隔离，减少对旧模式装配的不必要影响。

新服务对无新模式标记的任务采用旧路径，旧入口对新标记任务拒绝。停用新路由后仍保留所有新历史/领取，未结算任务不交给旧执行器。不能直接滚回旧二进制让它不认识新标记继续服务；升级所有可信入口后才启用新模式，回退需支持“新模式只读、拒绝写”的兼容版本。业务仍仅支持一个进程的共享Store，不因PostgreSQL领取声称多实例可继续。
